## Elevator pitch

> What are you proposing to change?

ACP needs a standard remote transport. We propose two **deliberately different** profiles on a single `/acp` endpoint, each optimized for a different deployment model:

- **Streamable HTTP (POST/GET/DELETE) — fully stateless.** No transport-level connection identity, no node-local state. Every request carries everything the server needs to route it (session id + auth). Server→client messages flow on the **per-POST SSE response** of the request that triggered them, with `GET` available only to **resume** an interrupted stream via `Last-Event-ID`. Designed to run behind any standard L7 load balancer with zero sticky-session requirements.
- **WebSocket upgrade (GET with `Upgrade: websocket`) — stateful, bidirectional, single-node.** A persistent full-duplex channel for low-latency interactive use. State naturally lives on the node that owns the socket; sticky routing is implicit in the upgrade.

Clients that support remote ACP over HTTP MUST support both profiles. Servers MAY support only one. The two profiles deliberately diverge: choose Streamable HTTP for horizontally-scaled cloud deployments, choose WebSocket for low-latency desktop/local clients.

Both profiles share the same JSON-RPC message format and ACP lifecycle as the existing **stdio** local subprocess transport.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

ACP only has stdio. There is no standard remote transport, which causes fragmentation as implementers invent their own HTTP layers, leading to incompatible SDKs and deployments.

Earlier drafts of this RFD proposed a transport-level `Acp-Connection-Id` returned by `initialize`, with long-lived GET SSE streams (connection-scoped plus per-session) bound to that connection. In practice this design forces the HTTP transport to keep meaningful per-connection state in memory on the node that handled `initialize`:

- live JSON-RPC routing maps,
- pending server-to-client requests (`request_permission`, elicitation),
- SSE writer handles and replay buffers,
- the agent task that owns the connection.

That state cannot be transparently moved between nodes, so the transport effectively **requires sticky sessions** behind any load balancer, and the connection dies if its owner node dies. This mirrors the problem the MCP transport working group is now addressing in SEP-2575 ("Make MCP Stateless") and related SEPs. We want ACP's HTTP profile to be stateless by construction so it composes cleanly with normal cloud infrastructure (multi-node, autoscaling, rolling deploys). WebSocket retains the stateful model because that's what a persistent socket *is*.

## What we propose to do about it

> What are you proposing to improve the situation?

### 1. Adds a stateless Streamable HTTP transport

The HTTP profile is designed so that **any node behind a load balancer can serve any request** with no node-local state and no sticky routing. Concretely:

1. **No transport-level connection identity.** There is no `Acp-Connection-Id` on HTTP. The only identifier the transport carries is `Acp-Session-Id` (returned by `session/new`), which is a durable identifier resolvable from shared agent state. `initialize` is reduced to a stateless capability negotiation: the client POSTs `initialize`, the server returns capabilities synchronously as JSON, and there is nothing to "bind" on the transport afterwards. Servers MUST return deterministic capabilities given their configuration so that any node returns the same answer.

2. **Per-POST SSE responses, not long-lived GET streams.** Client→server messages are sent via POST. For methods that produce streaming output or may trigger server-to-client requests (notably `session/prompt`), the POST response itself is an SSE stream (`Content-Type: text/event-stream`) carrying notifications, any server-to-client requests, and finally the JSON-RPC response to the originating POST. For methods with no streaming (e.g., `session/cancel`, `initialize`, permission responses, elicitation responses), the POST returns `200 OK` with a JSON body. Pure notifications return `202 Accepted`. This shape mirrors MCP Streamable HTTP and makes each HTTP exchange independently routable.

3. **Server-to-client requests are correlated through durable session state.** When the server emits a `request_permission` (or elicitation) on a POST's SSE response, it persists the pending request to the shared session store keyed by `(sessionId, jsonrpcId)`. The client replies with a separate POST containing `{ id, result }` and the `Acp-Session-Id` header. Any node can resolve and complete the pending request from the shared store. No node-local routing map is required.

4. **`GET` exists only for resumability.** A client whose POST SSE stream is interrupted MAY reopen it with `GET /acp`, the `Acp-Session-Id` header, and `Last-Event-ID`. The server replays events from durable per-session storage (keyed by `sessionId`) and continues the stream. There is no "open a stream and leave it open" pattern in the stateless profile — every SSE stream is the response to a specific POST (or a resume of one).

5. **HTTP/2 is RECOMMENDED, not required.** Without long-lived connection-scoped GET streams, HTTP/1.1 keep-alive is sufficient for the stateless profile. HTTP/2 remains beneficial for concurrent in-flight POSTs (e.g., a streaming `session/prompt` SSE response while the client also POSTs a permission response or `session/cancel`).

### 2. Adds WebSocket as the stateful, bidirectional profile

A GET with `Upgrade: websocket` upgrades to a persistent bidirectional channel on the same `/acp` endpoint.

WebSocket is **explicitly the stateful option**. The socket itself is the connection; the node that accepts the upgrade owns it for its lifetime. Server-to-client requests, notifications, and responses all flow on the socket in full duplex. State affinity is intrinsic to the transport — no shared session store is required for the lifetime of the socket. This is the recommended profile for desktop clients and any deployment where a single agent node can own the channel.

WebSocket retains an `Acp-Connection-Id` returned in the `101 Switching Protocols` headers; it is meaningful only for the duration of that socket and is never carried on HTTP POST/GET/DELETE.

### 3. Cookie support

Clients MUST accept, store, and return cookies set by the server on both profiles. Cookies on the stateless HTTP profile are intended for **auth, CDN, and WAF concerns** — the protocol itself never requires sticky routing on HTTP. Servers MUST NOT rely on cookies to recover transport state. On WebSocket, cookies behave as normal browser cookies for the lifetime of the upgrade.

### 4. Defines a unified routing model

| Method   | Upgrade Header?      | Behavior                                                                                                                                                                                |
| -------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST`   | —                    | Send a JSON-RPC message. Streaming methods return `200 OK` with `Content-Type: text/event-stream`; non-streaming requests return `200 OK` with a JSON body; notifications return `202 Accepted`. |
| `GET`    | No                   | **Resume only.** Requires `Acp-Session-Id` and `Last-Event-ID`. Replays missed events from durable storage on the session's most recent streaming POST, then continues the stream.       |
| `GET`    | `Upgrade: websocket` | Upgrade to WebSocket for stateful full-duplex messaging.                                                                                                                                |
| `DELETE` | —                    | Terminate a session. Requires `Acp-Session-Id`. Idempotent against the shared session store.                                                                                            |

### 5. Preserves the full ACP lifecycle

The `initialize` → `initialized` → messages → close lifecycle is identical regardless of transport. On WebSocket, lifecycle phases bind to the socket. On stateless HTTP, lifecycle phases bind to the `sessionId`: `initialize` negotiates capabilities for the *request* only (no binding), `session/new` returns the durable `sessionId`, subsequent POSTs carry `Acp-Session-Id` and route via shared state, `DELETE` ends the session.

## Shiny future

> How will things play out once this feature exists?

- **SDK implementers** get a clear, testable transport spec — Rust, TypeScript, and Python SDKs can all interoperate.
- **Desktop clients** use WebSocket for low-latency streaming; all clients support it as a baseline.
- **Cloud deployments** expose agents behind ordinary L7 load balancers with no sticky-session configuration. Any node can serve any HTTP request; node failure during a stream is recoverable via `Last-Event-ID` resume.
- **Proxy chains** can route ACP traffic over HTTP for multi-hop agent topologies. Stateless requests compose cleanly with normal HTTP intermediaries.

### Transport Architecture

```
                         ┌─────────────────────────────────┐
                         │         /acp endpoint           │
                         └──────┬──────────┬───────────────┘
                                │          │
                    ┌───────────▼──┐  ┌────▼──────────────┐
                    │  Stateless   │  │  WebSocket State   │
                    │  HTTP node   │  │  (per-socket, in-  │
                    │  (any node)  │  │   memory on owner) │
                    └───────┬──────┘  └────┬──────────────┘
                            │              │
                ┌───────────▼──┐            │
                │ Shared session│           │
                │ store (Redis/ │           │
                │ DB): sessions,│           │
                │ pending svr→  │           │
                │ client reqs,  │           │
                │ event log     │           │
                └───────┬──────┘            │
                        │                   │
                    ┌───▼───────────────────▼───────────────┐
                    │     ACP Agent (JSON-RPC handler)      │
                    │     serve(agent, read, write)         │
                    └───────────────────────────────────────┘
```

On the stateless HTTP profile, the per-node process holds no transport state. All session-scoped state — registered sessions, pending server-to-client requests, and the per-session SSE event log used for resume — lives in a shared store and is read/written on each request. On WebSocket, all state lives in process on the node owning the socket.

### Identity Model

The two profiles use different identifiers:

**Stateless HTTP profile**

- **`Acp-Session-Id`** (HTTP header) — Session-level identifier returned in the `session/new` response body. Required on every POST after `session/new` (including permission/elicitation responses), on every resume `GET`, and on `DELETE`. Resolvable from shared storage by any node.
- **`sessionId`** (JSON-RPC field) — Mirrors `Acp-Session-Id` inside JSON-RPC `params` for session-scoped methods and inside responses. The two MUST agree.
- There is **no `Acp-Connection-Id`** on the stateless HTTP profile. `initialize` is a pure, idempotent capability query that returns capabilities synchronously and binds nothing.

**WebSocket profile**

- **`Acp-Connection-Id`** (HTTP header on the `101` upgrade response) — Identifies the socket. Meaningful only for the duration of the socket; never sent on POST/GET/DELETE.
- **`sessionId`** (JSON-RPC field) — Identifies sessions hosted on the socket. A socket may host multiple sessions.

#### Content Negotiation and Validation

- POST `Content-Type` **MUST** be `application/json` (415 otherwise).
- POSTs for methods that may stream **MUST** include `Accept: text/event-stream` in addition to `application/json`. The server chooses the response `Content-Type` based on whether streaming is needed.
- POSTs for session-scoped operations (`session/prompt`, `session/cancel`, `session/load`, permission/elicitation responses, etc.) **MUST** include the `Acp-Session-Id` header. The `sessionId` in the JSON-RPC params **MUST** match.
- `initialize` and `session/new` **MUST NOT** include `Acp-Session-Id`.
- GET requests without `Upgrade: websocket` **MUST** include `Acp-Session-Id` and `Last-Event-ID`; GETs are only used for resume. GETs without `Last-Event-ID` return 400.
- An unknown `Acp-Session-Id` returns 404.
- Batch JSON-RPC requests return 501.
- HTTP/2 is **RECOMMENDED**; HTTP/1.1 is supported.

### WebSocket Request Flow

#### Connection Establishment (GET with Upgrade)

```
Client                                    Server
  │  GET /acp                               │
  │  Upgrade: websocket                     │
  │────────────────────────────────────────►│
  │  HTTP 101 Switching Protocols           │
  │  Acp-Connection-Id: <uuid>              │
  │◄────────────────────────────────────────│
  │  ══════ WebSocket Channel ══════════════│
```

A new connection is created on upgrade. The `Acp-Connection-Id` is returned in the upgrade response headers. The client must still send `initialize` as the first JSON-RPC message over the WebSocket to negotiate capabilities before creating sessions.

#### Bidirectional Messaging

All messages are WebSocket text frames containing JSON-RPC. Binary frames are ignored. On disconnect, the server cleans up the connection and any associated sessions.

### Unified Endpoint Routing

```
GET /acp
  ├── Has Upgrade: websocket? → WebSocket handler (stateful, per-socket state on this node)
  └── No → Stateless resume handler
        ├── Missing Acp-Session-Id? → 400 Bad Request
        ├── Missing Last-Event-ID? → 400 Bad Request
        ├── Unknown Acp-Session-Id? → 404 Not Found
        └── Valid → Read event log from shared store, replay + continue

POST /acp
  ├── method == "initialize" → 200 OK + JSON capabilities (no state created)
  ├── method == "session/new" → Persist session to shared store, 200 OK + JSON
  ├── Session-scoped method:
  │     ├── Missing Acp-Session-Id? → 400 Bad Request
  │     ├── Unknown Acp-Session-Id? → 404 Not Found
  │     ├── Streaming method (e.g. session/prompt, session/load) → 200 OK, text/event-stream
  │     ├── Non-streaming request (e.g. permission response, elicitation response) → 200 OK, JSON
  │     └── Notification (e.g. session/cancel) → 202 Accepted
  └── (catch-all malformed) → 400 Bad Request

DELETE /acp
  ├── Has Acp-Session-Id? → Mark session terminated in shared store, return 202 (idempotent)
  └── No Acp-Session-Id? → 400 Bad Request
```

### Stateless HTTP State Model

The per-node process holds no transport state. All durable state lives in the shared session store:

```
SharedStore {
    sessions: Map<sessionId, SessionRecord>,
    pending_server_requests: Map<(sessionId, jsonrpcId), PendingRequest>,
    event_log: Map<sessionId, Vec<SseEvent>>,        // bounded; for Last-Event-ID resume
    pubsub: Channel<sessionId>,                      // wakes up streaming POST handlers
}

SessionRecord {
    session_id:        String,
    capabilities:      NegotiatedCapabilities,       // snapshotted from initialize semantics
    owner_node_hint:   Option<NodeId>,               // optional, advisory only
    agent_state_ref:   AgentStateHandle,             // pointer into durable agent state
    cancelled:         bool,
    created_at:        Timestamp,
    last_event_id:     u64,
}

PendingRequest {
    session_id:  String,
    id:          JsonRpcId,
    method:      String,
    params:      Value,
    created_at:  Timestamp,
}
```

Each streaming POST handler:

1. Validates `Acp-Session-Id` against `SharedStore.sessions`.
2. Drives the agent for that session (the agent's own durable state is reattached on demand from `agent_state_ref`).
3. Writes every emitted SSE event to `event_log[sessionId]` *before* flushing it to the wire, so resume works regardless of which node served the original stream.
4. For server-to-client requests, writes a `PendingRequest` row, then awaits either (a) a `pubsub` notification that another node received the client's response POST, or (b) the resume of this stream on another node.
5. Terminates the stream with the JSON-RPC response event.

The agent itself remains stateful, but its state is keyed by `sessionId` and reattached on demand — exactly the partitioning the agent already needs to do for `session/load`.

### WebSocket State Model

WebSocket retains the original in-memory model. The node owning the socket holds:

```
WebSocketConnection {
    connection_id:  String,                          // Acp-Connection-Id (from 101 headers)
    capabilities:   NegotiatedCapabilities,
    sessions:       HashMap<String, Session>,        // keyed by sessionId
    to_agent_tx:    mpsc::Sender<String>,
    from_agent_rx:  Arc<Mutex<Receiver<String>>>,
    handle:         JoinHandle<()>,
}
```

If the socket drops, the agent's durable state survives (same `agent_state_ref` model as above) and a new client can reattach via the stateless HTTP profile and `session/load`, or via a new WebSocket and `session/load`.

### Deviations from MCP Streamable HTTP

1. **No `initialize`-bound session.** ACP separates capability negotiation (`initialize`, idempotent) from session creation (`session/new`). MCP returns a session id from `initialize`; ACP returns capabilities only and creates sessions explicitly. This avoids implicit transport state and lets ACP host multiple sessions per client without re-`initialize`-ing.
2. **WebSocket extension.** MCP doesn't define WebSocket. ACP adds it as a required client capability. Clients MUST support WebSocket, and servers MAY support only WebSocket.
3. **Two profiles with different statefulness.** ACP explicitly defines a stateless HTTP profile and a stateful WebSocket profile, with documented tradeoffs, rather than treating WebSocket as an optional extension of one transport.
4. **No batch requests.** Returns 501. May be added later.

### Implementation Plan

1. **Phase 1 — Specification** (this RFD): Define the stateless HTTP profile and the WebSocket profile.
2. **Phase 2 — Reference Implementation**:
   - Single-node in-memory adapter implementing the `SharedStore` interface (for local dev and tests).
   - Redis-backed adapter implementing `SharedStore` (for multi-node deployments).
   - Reference server in Goose (`block/goose`) wiring both adapters behind a config flag.
3. **Phase 3 — SDK Support**:
   - Rust SDK (`sacp`): stateless POST/SSE client with automatic `Last-Event-ID` resume; WebSocket client.
   - TypeScript SDK: same surface.
   - Conformance tests that run the stateless suite against any `SharedStore` implementation.
4. **Phase 4 — Hardening**: Origin validation, `Acp-Protocol-Version`, batch requests, event log retention/GC policy, signed session IDs, security audit.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### Why is the HTTP profile stateless?

Earlier drafts kept transport state on the node that handled `initialize` (a connection record, SSE writers, pending request maps, the agent task). That forced sticky sessions and made any node failure fatal to a connection. Real deployments hit this immediately behind ordinary load balancers. A stateless HTTP profile lets any node serve any request, survives node loss via resume, and composes with autoscaling and rolling deploys. It also mirrors the direction MCP is moving (SEP-2575 and related SEPs).

### Why keep WebSocket stateful?

Because a WebSocket *is* stateful — there's no useful "stateless WebSocket." Forcing the WebSocket profile to coordinate through a shared store on every message would add latency for no benefit, since the socket itself is already pinned to a single node. WebSocket is the right pick for desktop clients and local low-latency use; the stateless HTTP profile is the right pick for horizontally-scaled servers.

### Why isn't WebSocket just "the only transport"?

WebSocket doesn't traverse all corporate proxies and CDNs reliably, and serverless platforms often can't host long-lived sockets at all. The stateless HTTP profile is the universal fallback.

### How are sessions identified?

`Acp-Session-Id` (HTTP header) plus `sessionId` (JSON-RPC field); they MUST agree. On WebSocket, sessions are addressed only by the JSON-RPC `sessionId`, because the socket itself replaces transport-level routing.

### Can a client have multiple sessions at once?

Yes. On stateless HTTP, each session is independent and any number can be in flight; each request carries its own `Acp-Session-Id`. On WebSocket, a single socket can host multiple sessions, addressed by `sessionId` in JSON-RPC bodies.

### How does the server distinguish WebSocket from HTTP on GET?

By inspecting the `Upgrade: websocket` header. This is standard HTTP behavior.

### What if the SSE stream from a streaming POST drops mid-response?

The client reopens the stream with `GET /acp`, the same `Acp-Session-Id`, and `Last-Event-ID` set to the last event it processed. The server replays missed events from the per-session event log in the shared store, then continues. Because event IDs are scoped to the session and persisted before being flushed, the same resume request can be served by any node.

### How are server-to-client requests (e.g. `request_permission`, elicitation) handled statelessly?

When the server emits one on a POST's SSE response, it writes a `PendingRequest` row to the shared store keyed by `(sessionId, jsonrpcId)`. The client replies with a normal POST containing `{ id, result }`. That POST may land on any node; it resolves the row, publishes on the session's pub/sub channel, and the streaming POST handler (on whatever node is serving it) wakes up and continues. If the streaming POST has dropped, the same mechanism unblocks on the resumed stream.

### How does this interact with authentication?

Authentication (see auth-methods RFD) is orthogonal and layered on top via HTTP headers, query parameters, or WebSocket subprotocols. `Acp-Session-Id` is a transport-level identifier, not an auth token. Servers SHOULD treat `sessionId`s as opaque, unguessable, and bound to the authenticated principal that created them.

### What about the `Acp-Protocol-Version` header?

Clients SHOULD include it on all requests after `initialize`. Not yet implemented; part of Phase 4 hardening.

### What alternative approaches did you consider?

- **Sticky sessions / load-balancer affinity.** Rejected as the *required* model: it weakens availability, fails on owner-node death, and pushes infra complexity onto every deployment. Sticky routing is still *allowed* (e.g., for performance) but the protocol does not depend on it.
- **Redis owner registry + cross-node proxying.** Rejected: preserves the in-memory transport but adds a fragile dependency on per-node reachability and still loses connections on owner death.
- **Long-lived per-connection GET streams (previous design).** Rejected for the HTTP profile because they require sticky routing by construction. Retained in spirit only as the WebSocket profile, which makes the statefulness honest.
- **Per-request SSE streams with no resume (raw MCP).** Rejected: SSE streams *will* drop, and dropping a multi-minute `session/prompt` with no resume story is unacceptable.
- **WebSocket only.** Rejected: doesn't work through all proxies and serverless platforms.

## Revision history

- **2025-03-10**: Initial draft based on the RFC template and goose reference implementation.
- **2026-04-01**: Introduced a two-header identity model: `Acp-Connection-Id` (returned at `initialize`, binds to the connection) and `Acp-Session-Id` (returned at `session/new`, scopes to a session). This addresses feedback that the original single `Acp-Session-Id` conflated transport binding with ACP session identity, and enables session-scoped GET listener streams for targeted server-to-client event delivery. Removed connection-scoped GET streams — all GET SSE listeners now require both `Acp-Connection-Id` and `Acp-Session-Id`.
- **2026-04-15**: Minor edits
- **2026-04-23**: Major revision to single long-lived GET stream model. Changed from per-request SSE streams to a single connection-scoped GET stream for all server→client messages. POST requests (except `initialize`) now return 202 Accepted immediately. `initialize` returns 200 OK with JSON response body. Required HTTP/2 for multiplexing. This change makes the HTTP usage more similar to WebSocket and supports better the bidirectional nature of ACP.
- **2026-05-04**: Split the single GET stream into two: a connection-scoped stream (GET with `Acp-Connection-Id`) for connection-level messages such as responses to `session/new` and `session/load`, and session-scoped streams (GET with `Acp-Connection-Id` + `Acp-Session-Id`) for session updates, server-to-client requests like `request_permission`, and responses to session-scoped POSTs. Routing happens on HTTP headers rather than JSON-RPC body inspection; per-session streams have independent lifetimes.
- **2026-05-26**: Major revision making the HTTP profile fully stateless. Removed `Acp-Connection-Id` from the HTTP profile entirely; `initialize` is now an idempotent capability query that creates no state. Replaced long-lived connection-scoped and session-scoped GET streams with per-POST SSE responses (streaming methods like `session/prompt` return `200 OK` with `Content-Type: text/event-stream`; non-streaming methods return JSON; notifications return 202). `GET` is now only used to resume an interrupted stream via `Last-Event-ID`. Server-to-client requests (`request_permission`, elicitation) are correlated through a shared session store rather than a node-local routing map. HTTP/2 downgraded from REQUIRED to RECOMMENDED. Added an explicit shared-store state model (sessions, pending server-to-client requests, per-session event log). WebSocket profile retained unchanged and explicitly framed as the stateful counterpart. Motivated by multi-node deployment issues with the previous design (see acp-stateless-discussion) and the direction of MCP SEP-2575 et al.
